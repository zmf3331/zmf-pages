# 1 进程和内存管理

## 1.1 进程基础

Linux 是一个多用户、多任务的操作系统，"多任务"在系统层面的实现方式就是——把 CPU 时间切成很小的时间片，让多个程序轮流使用 CPU。为了管理这些并发运行的程序，内核抽象出了"进程"这一概念。进程是程序在操作系统中的一次执行过程，也是系统进行资源分配和调度的基本单位。

### 1.1.1 进程与线程

程序（Program）是存放在磁盘上的静态指令集合；进程（Process）是程序的一次动态执行过程，拥有独立的虚拟地址空间、文件描述符表、信号处理方式等资源。

线程（Thread）是进程内部的一条执行流，是 CPU 调度的最小单位。同一进程内的多个线程共享该进程的地址空间、文件描述符等资源，但各自拥有独立的栈和寄存器上下文，因此创建线程的开销远小于创建进程。

从内核视角看，Linux 并没有为线程单独设计一套数据结构，而是统一用 `task_struct` 描述"任务"，线程本质上就是与其他进程共享部分资源的进程，内核称之为轻量级进程（LWP，Light Weight Process）。同一线程组内的线程拥有相同的 TGID（线程组 ID），也就是用户态看到的 PID。

### 1.1.2 进程的状态

进程在整个生命周期中会在不同状态之间切换，`ps` 的 `STAT` 列与 `top` 的状态列都反映进程当前状态，常见取值如下：

| 状态码 | 名称 | 含义 |
| ------ | ---- | ---- |
| `R` | Running / Runnable | 正在运行，或已就绪在运行队列中等待 CPU |
| `S` | Interruptible Sleep | 可中断睡眠，等待事件（IO 完成、信号等），最常见 |
| `D` | Uninterruptible Sleep | 不可中断睡眠，通常在等待磁盘 IO，不能被信号唤醒 |
| `T` | Stopped | 被作业控制信号（SIGSTOP / SIGTSTP）暂停 |
| `t` | Tracing Stop | 被调试器跟踪而停止 |
| `Z` | Zombie | 已退出，但父进程尚未回收其退出状态 |
| `I` | Idle | 空闲的内核线程 |
| `X` | Dead | 已消亡，几乎观察不到 |

`STAT` 列在状态码后还可能跟若干附加标记，可用于快速判断进程的调度属性与会话关系：

| 标记 | 含义 |
| ---- | ---- |
| `<` | 高优先级进程 |
| `N` | 低优先级（nice 值较大） |
| `L` | 部分内存被锁定（用于实时任务 / DMA） |
| `s` | 会话首进程（session leader） |
| `l` | 多线程进程 |
| `+` | 位于前台进程组 |

### 1.1.3 进程的父子关系与生命周期

Linux 中除 0 号进程（idle，由内核创建）和 1 号进程（systemd / init）外，所有进程都是由父进程"克隆"而来，依赖下面四个系统调用完成：

| 系统调用 | 作用 |
| -------- | ---- |
| `fork()` | 创建一个子进程，父子进程代码相同，通过返回值区分（父进程得到子进程 PID，子进程得到 0） |
| `exec()` | 用新的程序替换当前进程的代码段与数据段，进程号不变，shell 执行命令就是 fork + exec |
| `exit()` | 进程退出，释放大部分资源，但保留退出状态供父进程读取 |
| `wait()` / `waitpid()` | 父进程回收子进程的退出状态，回收后子进程的进程表项才被释放 |

由此引申出两个重要概念，也是日常排查中经常遇到的两种异常进程：

- **孤儿进程**：父进程先于子进程退出，子进程会被 1 号进程（systemd）收养并由其负责回收，通常不会造成危害
- **僵尸进程**：子进程已退出，但父进程没有调用 `wait()` 回收，导致进程号被占用、进程表项残留。僵尸进程不占用 CPU 和内存，但会持续消耗进程号资源，大量僵尸进程会耗尽 PID 上限。处理办法是修复或重启其父进程，直接 kill 僵尸进程是无效的

`ps -eo pid,ppid,stat,cmd | awk '$3 ~ /Z/'` 可以快速筛出僵尸进程，再通过 PPID 溯源到父进程；`ps -eo pid,ppid,stat,cmd | awk '$2 == 1'` 则用于查找被 systemd 收养的孤儿进程。

### 1.1.4 进程的优先级

Linux 中普通进程采用 CFS（Completely Fair Scheduler，完全公平调度）调度，用户态通过"谦让值" nice 来影响进程能分到的 CPU 份额：

| 项目 | 说明 |
| ---- | ---- |
| nice 取值范围 | `-20 ~ 19`，数值越小优先级越高，默认 `0` |
| 权限限制 | 普通用户只能调大 nice（降低优先级），只有 root 可以提高优先级 |
| PRI | 内核实际使用的优先级，普通进程满足 `PRI = 20 + nice` |
| 查看方式 | `ps -eo pid,ni,pri,cmd` 或 `top` 的 `NI` / `PR` 列 |

对于需要实时响应的场景（音视频、工业控制等），可以使用实时调度策略，通过 `chrt` 设置 `SCHED_FIFO` / `SCHED_RR` 以及实时优先级（`1 ~ 99`，数值越大越高）。实时进程会抢占所有普通进程，使用不当会导致系统失去响应，需要谨慎评估。

```bash
$ nice -n 10 /usr/local/bin/backup.sh           # 以 nice 10 启动(降低优先级)
$ renice -n 10 -p 12345                         # 调整已运行进程的 nice 值
$ renice -n -5 -p 12345                         # 提高优先级需要 root 权限
$ ionice -c2 -n7 -p 12345                       # 调整 IO 优先级(类别2为best-effort,级别0~7)
$ chrt -f 50 ./realtime_app                     # 以 SCHED_FIFO 优先级 50 运行
$ chrt -p 12345                                 # 查看进程当前的调度策略
```

> 💡 数据库、消息队列等对 IO 延迟敏感的进程，可考虑用 `ionice` 降低备份任务的 IO 优先级，避免备份拖慢在线业务。

## 1.2 进程查看

### 1.2.1 ps 静态查看

ps 是"快照"式工具，只在执行的那一瞬间列出当时的进程信息。其参数风格分为 BSD 与 System V 两套，两套可以混用但容易出错，建议固定一种习惯。

```bash
$ ps aux                                    # BSD 风格,最常用:显示所有用户的所有进程
$ ps -ef                                    # System V 风格:显示所有进程,并带 PPID
$ ps -ef --forest                           # 以树形展示父子关系
$ ps -eo pid,ppid,user,stat,%CPU%,%MEM%,lstart,etime,cmd            # 自定义输出字段
$ ps -eo pid,%CPU%,%MEM%,cmd --sort=-%CPU | head -n 10           # 按 CPU 降序取前10
$ ps -eo pid,%CPU%,%MEM%,cmd --sort=-%MEM | head -n 5            # 按内存降序取前5
$ ps -eLf                                   # 显示线程(LWP),同一进程的多行 LWP 相同
$ ps -C nginx -o pid,user,%CPU%,%MEM%,cmd       # 按进程名过滤
$ ps -p 12345 -o pid,ppid,stat,etime,cmd    # 只看指定 PID
```

`ps aux` 输出字段含义：

| 字段 | 含义 |
| ---- | ---- |
| `USER` | 进程的属主 |
| `PID` | 进程号 |
| `%CPU` | 占用的 CPU 百分比（是整个生命周期的平均值，不代表瞬时值） |
| `%MEM` | 占用的物理内存百分比 |
| `VSZ` | 虚拟内存大小（含未实际分配的地址空间） |
| `RSS` | 常驻内存集，实际占用的物理内存 |
| `TTY` | 关联的终端，`?` 表示无控制终端（多为守护进程） |
| `STAT` | 进程状态，见 1.1 节 |
| `START` | 进程启动时间或日期 |
| `TIME` | 累计占用的 CPU 时间 |
| `COMMAND` | 启动命令，带 `[]` 表示内核线程 |

### 1.2.2 top 动态查看

top 会周期性地刷新进程列表，是登录服务器后最先使用的工具，默认 3 秒刷新一次。顶部五行是判断系统整体状况的第一手信息。

```bash
$ top                                       # 默认按 CPU 排序
$ top -d 1 -p 12345                         # 1秒刷新,只看指定 PID
$ top -u zmf                                # 只看指定用户
$ top -bn1 | head -n 20                     # 批处理模式取一次快照,适合脚本采集
```

top 输出前五行的关键字段：

| 行 | 关键字段 | 含义 |
| -- | -------- | ---- |
| 第一行 | `load average` | 过去 1、5、15 分钟的平均负载，等于"可运行 + 不可中断"的任务数 |
| 第二行 | `Tasks` | 进程总数，以及 running / sleeping / stopped / zombie 各状态数量 |
| 第三行 | `%Cpu(s)` | `us` 用户态、`sy` 内核态、`ni` nice 调整、`id` 空闲、`wa` 等待 IO、`hi` 硬中断、`si` 软中断、`st` 被虚拟化偷走 |
| 第四行 | `MiB Mem` | `total` 总内存、`free` 完全空闲、`used` 已使用、`buff/cache` 缓存 |
| 第五行 | `MiB Swap` | 交换分区总量、已用、可用 |

> 💡 判断负载是否过高，要看**负载值 ÷ CPU 核心数**，而不是负载值本身。例如 4 核机器负载 4.0 表示基本跑满，8 核机器负载 4.0 则相当空闲。

常用交互式快捷键（在 top 界面按 `h` 可查看全部）：

| 按键 | 作用 |
| ---- | ---- |
| `1` | 展开 / 收起每个 CPU 核心的使用率 |
| `P` | 按 CPU 使用率排序（默认） |
| `M` | 按内存使用率排序 |
| `T` | 按累计 CPU 时间排序 |
| `c` | 切换显示完整命令行 / 仅命令名 |
| `H` | 显示线程（切换后单个多线程进程可能占多行） |
| `k` | 提示输入 PID 并发送信号（默认 SIGTERM），最常用的"top 内杀进程" |
| `r` | 对指定 PID 执行 renice |
| `u` | 按用户过滤 |
| `f` | 进入字段管理界面，自定义显示列 |
| `W` | 把当前配置写入 `~/.toprc` 持久化 |
| `d` | 修改刷新间隔 |
| `q` | 退出 |

### 1.2.3 增强监控工具 htop / atop / glances

top 功能有限，日常运维更推荐下列工具，尤其是故障复盘时 atop 保留的历史快照。atop 的守护进程会按天保存性能快照，默认保留 28 天，是"昨天下午系统为什么卡"这类问题的唯一答案来源。

```bash
# 安装
$ yum -y install htop atop glances
# apt -y install htop atop glances

$ htop                                      # 交互友好,支持鼠标,顶部有 F1~F10 功能键
$ htop -u zmf -p 12345                      # 过滤用户与 PID
$ atop -n 1 -d                              # 采集一次后退出
$ atop -r /var/log/atop/atop_20261008       # 回放指定日期的历史日志(定位历史故障必用)
$ atop -r /var/log/atop/atop_20261008 -b 14:30   # 从指定时间点开始回放
$ glances                                   # 一体化监控,支持 Web 与 API 输出
```

htop 与 atop 的取舍：htop 更适合交互式排查与杀进程，atop 更适合事后追溯。atop 常用交互键如下：

| 按键 | 作用 |
| ---- | ---- |
| `g` | 切换到常规进程视图 |
| `d` | 切换到磁盘视图 |
| `m` | 切换到内存视图 |
| `n` | 切换到网络视图 |
| `c` | 切换到命令行视图 |
| `t` / `T` | 按时间跳转 / 定位到指定时刻 |
| `b` | 向后 / 向前选择时间点 |

### 1.2.4 pstree / pgrep / pidof

```bash
$ pstree -p                                 # 树形显示进程,并标出 PID
$ pstree -p 12345                           # 只看某个进程的子进程树
$ pstree -u                                 # 显示用户切换(线程/子进程属主变化)
$ pgrep -a sshd                             # 按名称匹配进程,并打印完整命令行
$ pgrep -u zmf -l                           # 指定用户,打印进程名
$ pgrep -f "jar app.jar"                    # 按完整命令行匹配(可定位 java 这类通用进程名)
$ pidof nginx                               # 按可执行文件名取 PID
$ pgrep -c -u zmf java                      # 统计匹配到的进程数量
```

> ⚠️ `pkill` / `pgrep -f` 按命令行匹配时，匹配范围包含自身所在的 shell 命令行，容易"误杀自己"。建议先用 `pgrep -af` 确认匹配结果，再执行 `pkill`。

## 1.3 进程控制

### 1.3.1 前台 / 后台 / 作业控制

Shell 的作业控制让同一个终端可以同时管理多个任务。在命令尾部加 `&` 即可把命令放到后台运行，此时终端会立刻返回、可以继续输入下一条命令。

```bash
$ tar -czf backup.tar.gz /data &            # 放到后台执行
[1] 20481
$ jobs                                      # 查看当前 shell 的作业列表
[1]+  Running                tar -czf backup.tar.gz /data &
$ fg %1                                    # 把 1 号作业调回前台
$ bg %1                                    # 让暂停的 1 号作业在后台继续运行
$ kill %1                                  # 按作业号发送 SIGTERM
```

键位操作是日常使用频率最高的部分：

| 操作 | 作用 |
| ---- | ---- |
| `Ctrl+Z` | 把当前前台进程挂起并放入后台（状态变为 Stopped） |
| `Ctrl+C` | 向前台进程组发送 SIGINT，中断程序 |
| `Ctrl+\` | 向前台进程组发送 SIGQUIT，并生成 core dump |
| `Ctrl+D` | 发送 EOF，通常用于退出交互式 shell 或结束输入 |
| `Ctrl+S` / `Ctrl+Q` | 暂停 / 恢复终端屏幕输出（容易误按成"卡死"） |

> ⚠️ `&` 启动的进程仍隶属于当前终端。直接关闭终端会向这些进程发送 SIGHUP，导致任务中断。需要真正脱离终端运行，应使用 `nohup`、`setsid` 或 `disown`，长期运行的服务则应交给 systemd 管理。

### 1.3.2 信号与 kill

信号是 Linux 进程间通信最基础的方式，也是运维"重启前先杀进程"的核心手段。

```bash
$ kill -l                                   # 列出所有信号编号与名称
$ kill 12345                                # 默认发送 SIGTERM(15),允许进程优雅退出
$ kill -9 12345                             # 发送 SIGKILL,强制杀死,进程无法捕获
$ kill -HUP 12345                           # 发送 SIGHUP,多数服务用其重新加载配置
$ kill -USR1 12345                          # 发送 SIGUSR1,常用于触发日志切割
$ pkill -f "python3 worker.py"              # 按命令行批量发送信号
$ killall nginx                             # 按进程名批量发送信号(要求名称完全匹配)
```

常用信号：

| 编号 | 名称 | 说明 |
| ---- | ---- | ---- |
| 1 | `SIGHUP` | 终端挂断 / 让服务重读配置，常用于 `nginx -s reload` 等场景 |
| 2 | `SIGINT` | 中断，等同 `Ctrl+C` |
| 3 | `SIGQUIT` | 退出并生成 core dump |
| 9 | `SIGKILL` | 强制杀死，不可捕获、不可忽略 |
| 15 | `SIGTERM` | 默认终止信号，可被捕获，应优先使用 |
| 18 | `SIGCONT` | 让暂停的进程继续运行 |
| 19 | `SIGSTOP` | 暂停进程，不可捕获 |
| 20 | `SIGTSTP` | 终端挂起，等同 `Ctrl+Z` |

> 💡 正确的杀进程顺序是"先 `kill 15` 等待，超时后再 `kill -9`"。直接 `kill -9` 会跳过清理逻辑，可能导致数据库连接未释放、临时文件残留、分片数据丢失等问题。

### 1.3.3 脱离终端的后台运行

`nohup`、`setsid`、`disown` 三者解决的是同一类问题——让进程不再受终端关闭（SIGHUP）影响，但手段与适用场景不同。

```bash
$ nohup /usr/local/bin/start.sh > /var/log/start.log 2>&1 &      # 忽略 SIGHUP,输出重定向到文件
$ setsid /usr/local/bin/daemon.sh                                # 新建会话,彻底脱离终端
$ disown -h %1                                                  # 把已启动的作业从作业表移除(不再收 SIGHUP)
$ screen -dmS job /usr/local/bin/long-run.sh                     # 交给 screen 托管(见 5 终端复用方法)
$ tmux new -d -s deploy /usr/local/bin/deploy.sh                 # 交给 tmux 托管(见 5 终端复用方法)
```

| 方式 | 原理 | 适用场景 |
| ---- | ---- | -------- |
| `nohup cmd &` | 忽略 SIGHUP，未重定向时输出写入 `nohup.out` | 临时跑一个耗时脚本 |
| `setsid cmd` | 新建会话与进程组，进程不再是终端的会话成员 | 需要彻底脱离终端的守护进程 |
| `disown %1` | 把作业从 shell 作业表移除，后续 `jobs` 看不到 | 命令已经跑起来才发现忘了加 nohup |
| `screen` / `tmux` | 由复用器持有会话，可随时切回查看 | 交互式长任务、需要随时回看输出 |

> ⚠️ `nohup` 只解决"收到 SIGHUP"的问题，不解决"进程与终端绑定"的问题。若进程仍会读写终端，关闭终端后可能收到 SIGTTIN / SIGTTOU 而被暂停，此时用 `setsid` 或复用器更稳妥。

### 1.3.4 切换用户执行

```bash
$ su - zmf                                   # 切换到 zmf 用户并加载其登录环境(需要密码)
$ runuser -l zmf -c "whoami"                 # root 专用,不需要密码,适合脚本中使用
$ sudo -u zmf /usr/local/bin/deploy.sh       # 以 zmf 身份执行指定命令
$ sudo -i                                    # 切换到 root 的登录环境
$ sudo -l                                    # 查看当前用户被授予的 sudo 权限
$ id -u -n                                   # 查看当前有效用户
$ ps -o user= -p $$                          # 查看当前 shell 的有效用户
$ loginctl list-sessions                     # 查看当前登录会话
```

> 💡 `su -` 与 `su` 的区别：带 `-` 会重新加载目标用户的环境变量与工作目录，写运维脚本时应始终使用 `su -`，避免继承到不干净的环境。

## 1.4 内存管理

### 1.4.1 虚拟内存与地址空间

每个进程都拥有独立的虚拟地址空间，CPU 发出的是虚拟地址，由 MMU（内存管理单元）配合页表翻译成物理地址。这样做带来三点好处：进程之间彼此隔离、可以使用比物理内存更大的地址空间、便于内存共享与按需分配。

进程虚拟地址空间的典型划分：

| 区域 | 说明 |
| ---- | ---- |
| 代码段 text | 存放可执行指令，通常只读 |
| 数据段 data / bss | 已初始化 / 未初始化的全局变量与静态变量 |
| 堆 heap | 由 `malloc` / `new` 动态分配，向高地址增长 |
| 内存映射区 mmap | 动态库、文件映射、大块 `malloc` 分配 |
| 栈 stack | 局部变量与函数调用上下文，向低地址增长 |

物理内存的管理单位是**页**（Page，通常 4KB）：内核用伙伴系统（buddy system）管理页框，用 slab 分配器缓存常用内核对象，用页表与 TLB 加速地址翻译。当物理内存不足时，内核会把不常访问的页写入 swap 或直接丢弃（文件页），这个过程称为页面回收。

按背后是否有磁盘文件，内存页可以分为三类，理解这个分类是看懂 `free` 输出的前提：

| 类型 | 说明 | 示例 |
| ---- | ---- | ---- |
| 匿名页 | 没有对应磁盘文件，只能换出到 swap | 堆、栈、`malloc` 分配的内存 |
| 文件页 | 由磁盘文件映射而来，可直接丢弃后重新读取 | 可执行文件、动态库、被读写过的数据文件 |
| 共享内存 | 多进程映射同一块物理内存 | `/dev/shm`、SysV `shmget` |

```bash
$ cat /proc/12345/maps                       # 查看某个进程的虚拟地址空间布局
$ pmap -x 12345                             # 更易读的地址空间与内存占用明细
$ smem -tk                                  # 按进程统计 PSS(精确的物理内存占用工具)
$ cat /proc/12345/status | grep -E "VmSize|VmRSS|VmSwap"       # 进程内存总览
```

### 1.4.2 free 与内存构成

`free` 是查看内存的第一命令，但它的输出最容易被误读——`free` 列几乎永远是"很小"的，因为 Linux 会主动把空闲内存拿去做缓存，"空闲内存被浪费"才是问题。

```bash
$ free -h
               total        used        free      shared  buff/cache   available
Mem:            15Gi       6.2Gi       1.1Gi       180Mi       8.2Gi       8.9Gi
Swap:          4.0Gi       0.0Ki       4.0Gi

$ free -m                                   # 以 MB 为单位
$ free -s 1                                 # 每秒刷新一次
$ cat /proc/meminfo                         # 最原始的内存明细
```

| 列 | 含义 |
| -- | ---- |
| `total` | 物理内存总量 |
| `used` | 已使用内存（已经扣除了可回收的 buff/cache） |
| `free` | 完全空闲的内存，通常很小 |
| `shared` | 多进程共享的内存，主要是 `tmpfs` / `/dev/shm` |
| `buff/cache` | 内核缓冲区与页缓存，内存紧张时大部分可被回收 |
| `available` | **估算的可用内存**，包含可回收的缓存，是判断"还够不够"的关键指标 |

> 💡 判断内存是否真的不足看 `available`；杀掉进程后 `free` 没明显增加，说明内存被缓存占用，也属于正常现象。

`/proc/meminfo` 中需要重点关注的字段：

| 字段 | 说明 |
| ---- | ---- |
| `MemAvailable` | 同 `free` 的 available 列 |
| `Dirty` | 已修改但尚未回写磁盘的页，持续偏大说明 IO 压力大 |
| `Writeback` | 正在回写磁盘的页 |
| `Slab` / `SReclaimable` / `SUnreclaim` | 内核对象缓存，SReclaimable 可回收，SUnreclaim 不可回收，后者持续增长多为内核泄漏 |
| `AnonPages` | 匿名页总量 |
| `Committed_AS` / `CommitLimit` | 已承诺的内存与承诺上限，比值长期超过 100% 需警惕 |
| `HugePages_Total` | 大页数量，Oracle 等数据库会依赖 |

### 1.4.3 交换空间（Swap）与 OOM

swap 是磁盘上的一块空间，用于在物理内存紧张时存放被换出的匿名页。它的作用不是"扩展内存"，而是给内存峰值留出缓冲，避免直接触发 OOM。需要说明的是，swap 的读写速度远低于物理内存，一旦系统频繁换页（swap in/out 很高），性能会断崖式下降。

| 项目 | 说明 |
| ---- | ---- |
| swappiness | 内核参数 `/proc/sys/vm/swappiness`，取值 0~100，表示换出匿名页的倾向，默认 60，数据库服务器常调低到 10 |
| swap 分区 | 安装系统时划分，分区类型为 swap |
| swap 文件 | 后期扩容更灵活，可随用随建 |

```bash
# 创建一个 4G 的 swap 文件并启用
$ dd if=/dev/zero of=/swapfile bs=1M count=4096
$ chmod 600 /swapfile
$ mkswap /swapfile
$ swapon /swapfile
$ free -h

# 写入 /etc/fstab 持久化,开机自动启用
$ echo "/swapfile none swap sw 0 0" >> /etc/fstab

# 关闭并删除
$ swapoff /swapfile
$ rm -f /swapfile

$ swapon -s                                 # 查看当前 swap 使用情况
$ sysctl vm.swappiness                      # 查看当前倾向值
$ sysctl -w vm.swappiness=10                # 临时调整
$ grep -n "vm.swappiness" /etc/sysctl.conf  # 检查是否已持久化
```

当物理内存与 swap 都耗尽时，内核的 OOM Killer（Out Of Memory Killer）会按 `oom_score` 选择"最该被杀"的进程并发送 SIGKILL。因此进程莫名消失、退出码为 137，多半是被 OOM 杀掉了。

```bash
$ dmesg -T | grep -i -E "oom|killed process"    # 查看 OOM 记录
$ grep -i "oom" /var/log/messages               # CentOS 系
$ grep -i "oom" /var/log/syslog                 # Debian 系
$ cat /proc/12345/oom_score                     # 进程的 OOM 分值,越大越容易被杀
$ cat /proc/12345/oom_score_adj                 # 人工调整值,-1000 表示永不被杀
$ echo -1000 > /proc/12345/oom_score_adj        # 临时保护关键进程
```

> 💡 对于 systemd 管理的服务，可以在 unit 中用 `OOMScoreAdjust=-1000` 永久保护关键进程，比手工写 `/proc` 更可靠。同时在 `/etc/systemd/system/*.service` 中通过 `MemoryMax=` 限制单个服务的内存上限，避免一个服务把整机内存吃光。

### 1.4.4 内存泄漏排查与手动释放

内存泄漏的表现是进程 RSS 随时间持续增长且不回落，即使没有业务流量。定位思路是先区分"真泄漏"还是"缓存未回收"，再逐层缩小范围。

```bash
$ ps -eo pid,%CPU%,%MEM%,rss,cmd --sort=-rss | head            # 找 RSS 最大的进程
$ for i in 1 2 3; do ps -o rss= -p 12345; sleep 60; done           # 观察 RSS 是否持续增长
$ pmap -x 12345 | tail -n 5                                        # 看内存映射汇总
$ smem -tk -P java                                                 # 按 PSS 统计,比 RSS 更准确
$ pmap -x 12345 | sort -k3 -n -r | head -n 10                      # 揪出最大的映射块
$ lsof -p 12345 | wc -l                                            # 排查文件描述符泄漏
$ cat /proc/12345/status | grep -E "VmRSS|VmSwap|Threads"          # 配合定时采样做趋势
```

| 场景 | 常见原因 | 处理方向 |
| ---- | -------- | -------- |
| Java 应用 | 堆外内存、元空间、线程泄漏、连接池未释放 | jmap / jstat / Arthas 分析堆与线程 |
| Nginx | 特定版本的缓慢泄漏 | 升级版本，或配置 worker 定期重启 |
| 自研服务 | 内存申请未释放、缓存无上限 | 定位代码并加内存上限，定期重启兜底 |
| 内核态 | Slab 中不可回收部分持续增长 | 排查内核模块与内核版本 Bug |

`lsof` 是排查"内存/句柄不释放"的关键工具，常见用法：

```bash
$ lsof -p 12345                             # 某进程打开的所有文件与网络连接
$ lsof /var/log/app.log                     # 谁占用了这个文件
$ lsof -i :8080                             # 谁占用了这个端口
$ lsof -i -sTCP:LISTEN                      # 列出所有监听中的端口
$ lsof +L1                                  # 找出已删除但仍被进程占用的文件(磁盘不释放的元凶)
```

> ⚠️ `lsof +L1` 常用于定位"删除了日志文件但磁盘空间没释放"的问题——文件被删除但仍被进程持有句柄时，空间不会归还，需要重启或 `truncate` 该文件。

手动释放缓存（`echo 3 > /proc/sys/vm/drop_caches`）会清空页缓存与 dentry/inode 缓存，导致后续 IO 变慢，只适合压测前统一环境或明确排查时使用，**不建议在生产环境当常规手段**。

```bash
$ sync                                      # 先落盘,避免丢数据
$ echo 1 > /proc/sys/vm/drop_caches         # 释放页缓存
$ echo 2 > /proc/sys/vm/drop_caches         # 释放 dentry 与 inode 缓存
$ echo 3 > /proc/sys/vm/drop_caches         # 全部释放
$ cat /proc/sys/vm/drop_caches              # 查看释放次数统计
```

# 2 进程管理和性能相关工具

## 2.1 系统整体性能工具

### 2.1.1 平均负载与 uptime

`uptime` 一行输出就给出了系统已运行时间、登录用户数与平均负载，是"这台机器忙不忙"的第一判断。

```bash
$ uptime
 14:32:05 up 62 days,  3:11,  2 users,  load average: 0.52, 0.68, 0.71
$ uptime -p                                 # 人类可读的运行时长
$ uptime -s                                 # 系统启动时间
$ cat /proc/loadavg                         # 原始数据,末位是最近创建与总进程数
$ nproc                                     # CPU 核心数(判断负载高低的分母)
```

平均负载 = 运行队列中可运行的任务数 + 处于不可中断睡眠（`D`）的任务数。因此负载高不一定等于 CPU 忙，还可能是磁盘 IO 阻塞。三种典型的高负载场景：

| 现象 | 特征 | 方向 |
| ---- | ---- | ---- |
| CPU 密集型 | `us` 高、负载高 | 定位耗 CPU 的进程，考虑扩容或优化算法 |
| IO 密集型 | `wa` 高、`D` 状态进程多 | 用 iostat / iotop 定位磁盘瓶颈 |
| 大量进程堆积 | 负载远大于 `nproc` | 检查是否进程数失控或存在僵尸进程 |

### 2.1.2 vmstat 虚拟内存统计

vmstat 一次输出即可同时看到进程、内存、swap、IO、CPU 五类指标，是"第一现场"最常用的综合工具。

```bash
$ vmstat 1 5                                # 每秒采集一次,共 5 次
$ vmstat -s                                 # 以内存统计为主
$ vmstat -d                                 # 磁盘统计
$ vmstat -w 1                               # 宽格式输出,字段不易挤在一起
```

| 分区 | 字段 | 含义 |
| ---- | ---- | ---- |
| procs | `r` | 运行队列中的进程数，长期大于 `nproc` 说明 CPU 不足 |
| procs | `b` | 处于不可中断睡眠的进程数，长期大于 0 多为 IO 瓶颈 |
| memory | `swpd` | 已使用的 swap 大小 |
| memory | `free` | 空闲物理内存 |
| memory | `buff` / `cache` | 内核缓冲 / 页缓存 |
| swap | `si` / `so` | 每秒从 swap 换入 / 换出的大小，长期非 0 说明内存不足 |
| io | `bi` / `bo` | 每秒从块设备读入 / 写出的块数，反映磁盘压力 |
| system | `in` / `cs` | 每秒中断数与上下文切换数，`cs` 异常高通常是线程争用 |
| cpu | `us` / `sy` / `id` / `wa` / `st` | 用户态 / 内核态 / 空闲 / 等待 IO / 被虚拟化偷走的比例 |

> 💡 判断 IO 瓶颈的经典组合是 `b` 长期大于 0、`wa` 偏高、`bi` / `bo` 很大；判断 CPU 瓶颈则是 `r` 长期大于 `nproc`。

### 2.1.3 mpstat 多核 CPU 统计

`vmstat` / `top` 看的是所有核心的平均值，会掩盖"单核跑满"的问题，用 `mpstat -P ALL` 可以逐核查看（需要 `sysstat` 包）。

```bash
$ yum -y install sysstat
$ mpstat -P ALL 1 3                         # 每秒采样,展示每个核心
$ mpstat 1 10                               # 只看总体平均
$ mpstat -P ALL 1 | awk '$3 ~ /all|[0-9]/ && $NF+0 > 80'   # 简单筛出使用率偏高的核心
```

单核跑满常见于：程序是单线程、应用锁竞争激烈、软中断集中在一个核心（如网卡单队列）。此时增加 CPU 核心并不能提升性能，需要从架构或中断亲和性上解决。

### 2.1.4 pidstat 单进程资源统计

`pidstat` 可以按进程粒度统计 CPU、内存、IO、上下文切换，是 `top` 之外最有价值的补充，尤其适合"哪个进程在频繁切换/换页"。

```bash
$ pidstat 1 5                               # 每秒统计各进程的 CPU 使用
$ pidstat -p 12345 1                        # 只看指定进程
$ pidstat -u -r -d -w 1 5                   # 同时统计 CPU/内存/IO/上下文切换
$ pidstat -r 1 5                            # 内存:minflt 次缺页 / majflt 主缺页(需读盘)
$ pidstat -d 1 5                            # IO:读写速率与 IO 等待
$ pidstat -w -t 1 5                         # 线程级上下文切换(cswch 自愿/nvcswch 非自愿)
$ pidstat -G java 1 5                       # 按进程名过滤
```

| 字段 | 含义 | 排查价值 |
| ---- | ---- | -------- |
| `%usr` / `%system` | 用户态 / 内核态 CPU 占比 | `%system` 高说明系统调用或锁开销大 |
| `minflt/s` | 次缺页（无需读盘） | 属正常行为 |
| `majflt/s` | 主缺页（需要读磁盘） | 持续非 0 说明内存不足或内存映射不合理 |
| `VSZ` / `RSS` | 虚拟内存 / 常驻内存 | 判断进程是否吃内存 |
| `cswch/s` | 自愿上下文切换 | 高说明在等 IO 或锁 |
| `nvcswch/s` | 非自愿上下文切换 | 高说明被强制抢占，CPU 竞争激烈 |

### 2.1.5 iostat / iotop 磁盘 IO

```bash
$ iostat -x 1 3                             # 扩展统计,每秒一次,重点关注 %util
$ iostat -dxm 1                             # 以 MB 为单位,仅磁盘
$ iotop -oP                                 # 只显示真正有 IO 的进程
$ iotop -oPa -n 5 -d 1                      # 累计模式,适合排查持续写入
$ fio --name=test --rw=randread --size=512M --runtime=30 --filename=/tmp/test.img   # 压测磁盘
```

| 指标 | 说明 | 参考阈值 |
| ---- | ---- | -------- |
| `r/s` / `w/s` | 每秒读 / 写请求数（IOPS） | 与磁盘型号相关，SSD 远高于机械盘 |
| `rkB/s` / `wkB/s` | 每秒读 / 写吞吐 | 结合业务带宽评估 |
| `await` | 平均每次 IO 的等待时间（毫秒） | 机械盘持续大于 20ms、SSD 大于 5ms 需关注 |
| `aqu-sz` | 平均请求队列长度 | 持续偏大说明设备处理不过来 |
| `%util` | 设备忙碌时间百分比 | 长期接近 100% 即存在瓶颈 |

> 💡 `iostat -x` 中 `%util` 接近 100% 只说明"设备很忙"，是否成为瓶颈还要看 `await` 与业务侧的响应延迟。SSD 在队列深度较高时 `%util` 长期 100% 是正常现象。

### 2.1.6 sar 历史性能数据

`sar` 属于 sysstat 套件，配合 `systemctl enable --now sysstat` 后，每 10 分钟会把性能数据写入 `/var/log/sa/`（保存约一个月），是"故障已过去，但需要还原现场"的首选工具。

```bash
$ systemctl enable --now sysstat
$ sar -u 1 5                                # CPU 使用率
$ sar -u -f /var/log/sa/sa08                # 查看 8 号那天(当天)的数据
$ sar -r 1 3                                # 内存使用
$ sar -S 1 3                                # swap 使用
$ sar -b 1 3                                # IO 总体统计
$ sar -d 1 3                                # 逐设备 IO(较新版本支持)
$ sar -n DEV 1 3                            # 网卡流量
$ sar -n TCP,ETCP 1 3                       # TCP 连接与重传
$ sar -q 1 3                                # 队列长度与负载
$ sar -w 1 3                                # 上下文切换
$ sar -u -s 14:00:00 -e 15:00:00 -f /var/log/sa/sa08    # 只看指定时间段
```

### 2.1.7 dstat 全能替代

`dstat` 把 vmstat、iostat、netstat 等常用指标合并到一屏，输出更直观，适合做现场演示或快速判断。

```bash
$ yum -y install dstat
$ dstat                                      # 默认:CPU/磁盘/网络/分页/系统
$ dstat -tcmndyr                           # 加时间戳,并显示 CPU/内存/网络/磁盘/负载
$ dstat -t --top-cpu --top-mem --top-io    # 直接列出 TOP 消耗进程
$ dstat -tc --disk --disk-util --fs         # 磁盘相关组合
$ dstat -tn --socket --tcp                  # 网络与套接字
$ dstat -tcd 1 10 > /tmp/dstat.log          # 采集到文件,便于事后分析
```

## 2.2 进程跟踪与调试

### 2.2.1 strace 系统调用跟踪

`strace` 通过 ptrace 跟踪进程的系统调用，是"程序卡在哪里"最直接的答案。前提是进程在等待系统调用（绝大多数卡顿都属于此类），若进程在纯计算则 strace 看不出问题。

```bash
$ strace -p 12345                            # 附加到运行中的进程
$ strace -f -p 12345                        # 跟踪其所有子进程与线程
$ strace -c -p 12345                        # 只统计系统调用耗时排行(开销较小)
$ strace -T -tt -p 12345                    # 显示时间戳与每次调用耗时
$ strace -e trace=open,read,write -p 12345  # 只跟踪指定系统调用
$ strace -e trace=network -f -p 12345       # 只看网络相关调用
$ strace -o /tmp/strace.log -f -p 12345     # 输出到文件,信息量大时必用
$ strace -s 256 -p 12345                    # 加大字符串截断长度(默认32)
$ timeout 10 strace -f -o /tmp/s.log ./app  # 限时跟踪,避免长时间挂住
```

> ⚠️ strace 会让被跟踪进程变慢数倍甚至更多，且 `-f` 会放大开销。生产环境优先用 `-c`（只统计不打印）或限时执行，并在业务低峰期操作。

典型输出解读（每一行代表一次系统调用）：

```bash
$ strace -T -tt -f -p 12345
14:20:31.123456 openat(AT_FDCWD, "/etc/nginx/nginx.conf", O_RDONLY|O_CLOEXEC) = 5 <0.000021>
14:20:31.123500 read(5, "#user  nginx;\nworker_processes  auto;\n"..., 8192) = 4096 <0.000008>
14:20:31.123600 epoll_wait(4, [], 512, 1000) = 0 <1.000234>
```

- 第一列是时间戳，`<...>` 内是该次调用耗时
- `openat` 等为调用名，括号内是参数，`= 5` 是返回值（负数即出错，配合 `errno` 判断）
- `epoll_wait` 返回 0 且耗时接近超时值，说明进程处于"空转等待"，是 IO 阻塞型卡顿的常见特征

### 2.2.2 ltrace / perf / bpftrace

```bash
$ ltrace -p 12345                           # 跟踪库函数调用(如 malloc/free),定位内存问题
$ ltrace -c -p 12345                        # 库函数耗时排行
$ perf top                                  # 实时热点函数排行(需 linux-tools / perf 包)
$ perf record -F 99 -a -g -- sleep 30       # 全系统采样 30 秒
$ perf report -i perf.data                  # 查看采样结果(火焰图基础数据)
$ perf stat -p 12345 -- sleep 10            # 统计 IPC、缓存命中、分支预测等硬件事件
$ bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args.filename)); }'
```

| 工具 | 跟踪对象 | 典型用途 |
| ---- | -------- | -------- |
| strace | 系统调用 | 程序卡死、文件打不开、网络连不上 |
| ltrace | 库函数 | 内存分配异常、第三方库调用异常 |
| perf | CPU 采样 / 硬件事件 | 性能热点定位、火焰图 |
| bpftrace / bcc | 内核动态探针 | 无侵入观测内核与用户态事件，开销低 |

`perf` 与 `bpftrace` 属于 eBPF / 采样体系，对生产影响小，是当前线上排查的首选；`strace` 适合"确认到底卡在哪个调用上"这种精确问题。

### 2.2.3 Core Dump 与崩溃分析

程序因段错误（SIGSEGV）、非法指令等信号异常退出时会生成 core dump 文件，结合 gdb 可以精确定位崩溃位置，是排查偶发崩溃的关键。

```bash
$ ulimit -c unlimited                        # 放开 core 文件大小限制(仅当前会话)
$ ulimit -c                                 # 查看当前限制
$ cat /proc/sys/kernel/core_pattern          # 查看 core 文件命名规则与存放位置
$ sysctl -w kernel.core_pattern=/data/cores/core.%e.%p.%t     # 临时修改
$ echo "/data/cores/core.%e.%p.%t" >> /etc/sysctl.conf        # 持久化
```

`core_pattern` 常用占位符：

| 占位符 | 含义 |
| ------ | ---- |
| `%p` | 进程号 |
| `%e` | 可执行文件名 |
| `%t` | 崩溃发生的时间戳 |
| `%u` | 进程属主用户名 |
| `%s` | 产生 core 的信号编号 |

```bash
# 用 gdb 分析
$ gdb /usr/local/bin/app /data/cores/core.app.12345.1712345678
(gdb) bt                                    # 打印调用栈
(gdb) bt full                               # 带局部变量
(gdb) info registers                        # 查看崩溃时的寄存器
(gdb) thread apply all bt                   # 所有线程的调用栈

# 没有 gdb 时可以用系统自带工具看基本信息
$ file /data/cores/core.app.12345.1712345678    # 确认产生 core 的可执行文件与信号
```

> 💡 systemd-coredump 场景下 core 由 systemd 统一收集，用 `coredumpctl list` 列出、`coredumpctl gdb <PID>` 直接进入调试。

### 2.2.4 进程状态快照与 Java 常用工具

```bash
# 通用:保存进程现场,交给开发/厂商分析
$ gcore -o /tmp/core.app 12345              # 不杀进程,生成 core
$ kill -3 12345                             # Java 进程:输出线程栈到日志
$ jstack 12345 > /tmp/jstack.txt            # Java 线程栈
$ jmap -heap 12345                          # Java 堆使用概况
$ jmap -histo:live 12345 | head -n 20       # 存活对象直方图,定位内存大户
$ jstat -gcutil 12345 1000 10               # GC 统计,观察 Full GC 频率
$ jcmd 12345 VM.flags                       # 查看 JVM 启动参数
$ top -H -p 12345                           # 查看 Java 进程内的线程,结合 jstack 定位高 CPU 线程
```

定位"Java 进程 CPU 高"的标准姿势：

1. `top -H -p <PID>` 找出占用 CPU 最高的线程号
2. 把线程号转成十六进制：`printf "%x\n" 12346`
3. 在 `jstack` 输出中搜索该十六进制值，即可定位到具体代码行

# 3 计划任务和Systemd

## 3.1 计划任务

Linux 的计划任务有两套体系：传统的时间驱动工具（at / cron / anacron）与 systemd 的定时器（timer）。前者简单通用，后者与 systemd 的资源控制、日志体系天然集成，是新环境的首选。

### 3.1.1 一次性计划任务 at

`at` 用于"在某个时间点执行一次"的任务，依赖 `atd` 服务。

```bash
$ systemctl enable --now atd                # 确保 atd 服务已启动
$ yum -y install at

$ echo "/usr/local/bin/report.sh" | at 23:00                # 今晚 23 点执行
$ at -f /usr/local/bin/backup.sh 02:00 2026-10-09           # 从脚本文件读取任务
$ at now + 30 minutes                       # 30 分钟后执行
$ at teatime                                # 今天下午 16:00
$ atq                                       # 查看待执行的任务列表
$ at -c 2                                   # 查看 2 号任务的完整内容
$ atrm 2                                    # 删除 2 号任务
$ batch                                     # 在系统负载较低时执行(负载阈值默认 1.5)
```

交互式输入时，`Ctrl+D` 结束输入。`at` 的访问控制由 `/etc/at.allow` 与 `/etc/at.deny` 决定，优先看 allow 文件。

### 3.1.2 周期性计划任务 cron

cron 是最经典的计划任务工具，由 `crond` 守护进程每分钟检查一次任务表并执行到点的任务。

```bash
$ systemctl status crond                     # CentOS 服务名(部分发行版为 cron)
$ crontab -e                                # 编辑当前用户的任务表
$ crontab -l                                # 列出当前用户的任务
$ crontab -r                                # 删除全部任务(慎用,无确认提示)
$ crontab -u zmf -l                          # root 查看指定用户的任务
$ ls /var/spool/cron/                       # 各用户任务表的存放位置
$ ls /etc/cron.d/ /etc/cron.daily/          # 系统级任务目录
```

crontab 的格式为"分 时 日 月 周 + 命令"，五个时间字段的取值如下：

| 字段 | 取值范围 | 说明 |
| ---- | -------- | ---- |
| 分钟 | 0-59 | |
| 小时 | 0-23 | |
| 日 | 1-31 | |
| 月 | 1-12 | 也可以用 jan、feb 等英文缩写 |
| 星期 | 0-7 | 0 和 7 都表示周日，也可以用 sun、mon |

```bash
# 每天凌晨 2:30 执行备份
30 2 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1

# 每 5 分钟检查一次服务状态
*/5 * * * * /usr/local/bin/check_service.sh

# 每周一至周五 9 点到 18 点,每小时的第 0 分钟执行
0 9-18 * * 1-5 /usr/local/bin/report.sh

# 每月 1 号和 15 号凌晨执行
0 3 1,15 * * /usr/local/bin/monthly.sh

# 每 2 小时执行一次
0 */2 * * * /usr/local/bin/sync.sh

# 星期日的 23:00(注意:周字段与日字段不建议同时指定,容易产生歧义)
0 23 * * 0 /usr/local/bin/weekly.sh
```

常用特殊宏（与上面写法等价，可读性更好）：

| 宏 | 等价写法 | 说明 |
| -- | -------- | ---- |
| `@reboot` | - | 每次开机后执行一次 |
| `@yearly` / `@annually` | `0 0 1 1 *` | 每年 1 月 1 日 0 点 |
| `@monthly` | `0 0 1 * *` | 每月 1 日 0 点 |
| `@weekly` | `0 0 * * 0` | 每周日 0 点 |
| `@daily` / `@midnight` | `0 0 * * *` | 每天 0 点 |
| `@hourly` | `0 * * * *` | 每小时 |

> ⚠️ cron 任务的排查有三个高频坑：
> 1. **环境变量不同** —— cron 的 `PATH` 很短、没有 `~/.bashrc` 的环境，命令务必写绝对路径，或在脚本开头显式 `source` 环境文件
> 2. **输出被丢弃** —— 未重定向的输出会以邮件形式堆积（或直接丢失），调试阶段建议一律加 `>> xxx.log 2>&1`
> 3. **百分号需要转义** —— crontab 中 `%` 有特殊含义（表示换行），命令里若要用到 `%`（如 `date +%F`）必须写成 `\%`，否则任务会被截断

```bash
# 排查 cron 是否执行
$ grep CRON /var/log/cron                   # CentOS 系
$ grep CRON /var/log/syslog                 # Debian 系
$ systemctl status crond                    # 确认守护进程正常
$ tail -f /var/log/cron                     # 实时跟踪
```

### 3.1.3 anacron 与开机补跑

cron 的短板是"错过了就不补"。服务器关机期间到点的任务不会执行，`anacron` 正是为此设计——它按天/周/月为单位检查任务是否执行过，未执行则在开机后补跑。

```bash
$ cat /etc/anacrontab
SHELL=/bin/sh
PATH=/sbin:/bin:/usr/sbin:/usr/bin
MAILTO=root
RANDOM_DELAY=45                             # 随机延迟上限(分钟),避免多台机器同时执行
START_HOURS_RANGE=3-22                      # 允许执行的时间段
1    5    cron.daily     nice run-parts /etc/cron.daily      # 周期(天) 延迟(分) 任务名 命令
7    25   cron.weekly    nice run-parts /etc/cron.weekly
@monthly 45 cron.monthly nice run-parts /etc/cron.monthly
```

| 配置项 | 说明 |
| ------ | ---- |
| `RANDOM_DELAY` | 在延迟基础上再加随机分钟数，避免集群同时启动任务造成冲击 |
| `START_HOURS_RANGE` | 只有落在这个时间窗内才会执行补跑 |
| `/var/spool/anacron/` | 记录各任务上次执行日期，删除该文件会导致任务重复执行 |

### 3.1.4 systemd timer 定时任务

systemd 的定时器由一对 unit 组成：`.timer` 负责定时，`.service` 负责执行。相比 cron，它具备日志统一（journalctl 直接可查）、可指定用户与资源限制、支持单调时钟（如"开机后 5 分钟"）、可查看下次触发时间等优势。

```bash
$ systemctl list-timers --all                # 列出所有定时器及下次触发时间
$ systemctl status mytask.timer
$ systemd-analyze calendar "Mon *-*-* 03:00:00"   # 校验时间表达式是否正确

# 手动触发一次,验证 service 是否正常
$ systemctl start mytask.service
```

常见定时表达式：

| 表达式 | 含义 |
| ------ | ---- |
| `OnCalendar=daily` | 每天 00:00 |
| `OnCalendar=*-*-* 02:30:00` | 每天 02:30 |
| `OnCalendar=Mon..Fri *-*-* 09:00` | 工作日 09:00 |
| `OnCalendar=*:0/15` | 每 15 分钟 |
| `OnUnitActiveSec=1h` | 距上次激活 1 小时后（单调时钟，不受改时间影响） |
| `OnBootSec=5min` | 开机后 5 分钟 |

> 💡 `OnCalendar` 使用真实的墙钟时间，适合"每天凌晨 3 点备份"；`OnUnitActiveSec` 使用单调时钟，适合"每 30 分钟同步一次"这类不关心具体时刻的任务。

## 3.2 systemd 基础

systemd 是现代主流发行版（CentOS 7+、RHEL 7+、Ubuntu 16.04+、Debian 8+）的初始化系统与服务管理器，取代了传统的 SysV init。它采用并行启动、按需启动（socket / D-Bus 激活）、基于 cgroup 的资源控制等机制，大幅缩短了开机时间。

| 概念 | 说明 |
| ---- | ---- |
| Unit | systemd 的管理对象，用后缀区分类型，如 `.service`、`.timer`、`.socket`、`.target`、`.mount`、`.path` |
| Target | 一组 unit 的集合，用于替代运行级别，如 `multi-user.target`、`graphical.target` |
| Slice | 按树形结构划分的 cgroup 资源分组 |
| Unit 文件路径 | `/usr/lib/systemd/system/`（发行版自带）、`/etc/systemd/system/`（管理员自定义，优先级更高） |
| 依赖关系 | `Requires` / `Wants`（强弱依赖）、`After` / `Before`（仅顺序） |

### 3.2.1 systemctl 常用命令

```bash
$ systemctl start nginx                      # 启动
$ systemctl stop nginx                       # 停止
$ systemctl restart nginx                    # 重启(包含 stop + start)
$ systemctl reload nginx                     # 仅重新加载配置,不断开连接(服务需支持)
$ systemctl enable --now nginx               # 设置开机自启并立即启动(最常用组合)
$ systemctl disable --now nginx              # 取消自启并立即停止
$ systemctl status nginx                     # 查看运行状态与最近日志
$ systemctl is-active nginx                  # 是否正在运行(脚本中常用)
$ systemctl is-enabled nginx                 # 是否开机自启
$ systemctl list-units --type=service --state=running    # 列出所有运行中的服务
$ systemctl list-unit-files --type=service --state=enabled  # 列出所有已自启的服务
$ systemctl list-units --failed              # 列出所有失败的服务(排障第一步)
$ systemctl daemon-reload                    # 修改 unit 文件后必须执行
$ systemctl reset-failed nginx               # 清除失败计数,允许重新启动
$ systemctl cat nginx                        # 查看最终生效的 unit 内容(含 override)
$ systemctl show nginx -p ExecStart          # 查看某个具体属性

$ systemctl poweroff / reboot                # 关机 / 重启
$ systemctl get-default                      # 查看默认 target
$ systemctl set-default multi-user.target    # 设置默认为多用户命令行模式
$ systemctl isolate multi-user.target        # 立即切换 target(不影响默认值)
```

> ⚠️ 修改或新增 unit 文件后必须先执行 `systemctl daemon-reload`，否则 systemd 仍使用旧配置。而 `enable` 只负责建立开机启动的符号链接，不会重启服务。

### 3.2.2 Unit 文件结构与常用指令

一个 service unit 通常由 `[Unit]`、`[Service]`、`[Install]` 三段组成。

```bash
[Unit]
Description=My Application Server              # 描述,显示在 systemctl status 中
Documentation=man:systemd(1) https://example.com/docs   # 文档地址
After=network-online.target                   # 在本 unit 之后启动(仅顺序)
Before=shutdown.target
Wants=network-online.target                   # 弱依赖:依赖启动失败也不影响自身
Requires=postgresql.service                   # 强依赖:依赖停止时自身也会停止
Conflicts=httpd.service                       # 互斥:两者不能同时运行

[Service]
Type=simple                                   # 服务类型,见下表
User=appuser                                  # 运行身份
Group=appuser
WorkingDirectory=/opt/app                     # 工作目录
Environment="JAVA_HOME=/usr/java/default" "TZ=Asia/Shanghai"
EnvironmentFile=-/etc/sysconfig/myapp         # 从文件读取环境变量,前缀 - 表示文件不存在也不报错
ExecStartPre=/bin/bash -c 'test -f /opt/app/app.jar'   # 启动前检查
ExecStart=/usr/bin/java -jar /opt/app/app.jar  # 启动命令
ExecReload=/bin/kill -HUP $MAINPID             # 重载命令
ExecStop=/bin/kill -TERM $MAINPID              # 停止命令
Restart=always                                # 退出后总是重启
RestartSec=5                                  # 重启前等待秒数
TimeoutStopSec=30                             # 停止超时,超时后发送 SIGKILL
LimitNOFILE=65535                             # 文件描述符上限
LimitNPROC=65535                              # 进程数上限
MemoryMax=2G                                  # 内存上限,超过则触发 OOM
CPUQuota=200%                                 # CPU 配额,最多使用 2 个核心
OOMScoreAdjust=-500                           # 降低被 OOM 杀掉的概率
StandardOutput=journal                        # 标准输出写入 journal
StandardError=journal
KillMode=mixed                                # 停止时先发信号给主进程,超时后杀掉同组进程

[Install]
WantedBy=multi-user.target                    # enable 时把本服务挂到该 target 下
```

`[Service]` 段的 `Type` 决定了 systemd 如何判断服务"启动完成"：

| Type | 适用场景 |
| ---- | -------- |
| `simple` | 默认值，ExecStart 启动的进程即主进程（前台运行的程序） |
| `forking` | 主进程 fork 后父进程退出（传统守护进程、老式 init 脚本） |
| `oneshot` | 执行一次就结束的任务，常配合 `RemainAfterExit=yes` |
| `notify` | 进程通过 sd_notify 主动通知就绪（可靠性最高，如 Nginx 支持） |
| `dbus` | 通过 D-Bus 就绪 |
| `idle` | 等其他任务执行完再启动 |

`Restart` 的取值：

| 取值 | 说明 |
| ---- | ---- |
| `no` | 默认，不重启 |
| `on-success` | 仅在正常退出（退出码 0）时重启 |
| `on-failure` | 非正常退出、被信号杀死、超时时重启，业务服务的常用选择 |
| `on-abnormal` | 被信号杀死或超时时重启 |
| `always` | 无论何种原因退出都重启，守护性质的服务常用 |

### 3.2.3 编写一个 systemd 服务（完整示例）

以部署一个 Java 应用为例，从零到开机自启的完整流程：

```bash
# 1. 创建用户与目录
$ useradd -r -s /sbin/nologin appuser
$ mkdir -p /opt/app /var/log/app
$ chown -R appuser:appuser /opt/app /var/log/app

# 2. 编写 unit 文件
$ vim /etc/systemd/system/myapp.service
```

```bash
[Unit]
Description=My Java Application
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=appuser
Group=appuser
WorkingDirectory=/opt/app
Environment="TZ=Asia/Shanghai" "JAVA_OPTS=-Xms512m -Xmx1024m"
ExecStart=/usr/bin/java $JAVA_OPTS -jar /opt/app/app.jar --spring.profiles.active=prod
Restart=on-failure
RestartSec=10
SuccessExitStatus=143
LimitNOFILE=65535
StandardOutput=journal
StandardError=journal
KillMode=mixed
TimeoutStopSec=30

[Install]
WantedBy=multi-user.target
```

```bash
# 3. 加载、启动、设自启
$ systemctl daemon-reload
$ systemctl enable --now myapp
$ systemctl status myapp

# 4. 验证与排障
$ journalctl -u myapp -n 100 --no-pager
$ systemctl is-enabled myapp
$ systemctl list-units --failed
```

> 💡 `SuccessExitStatus=143` 用于把 Java 进程收到 SIGTERM 后的退出码 143 视为正常退出，避免 `systemctl stop` 被记录为失败（进而触发 `Restart`）。这个坑在 Java 服务上非常常见。

### 3.2.4 自定义服务覆盖与临时修改

不建议直接修改 `/usr/lib/systemd/system/` 下发行版自带的 unit（包升级会被覆盖），而应使用 `override` 或 `drop-in` 方式追加配置。

```bash
$ systemctl edit nginx                       # 创建 drop-in 覆盖文件并自动 daemon-reload
# 生成路径:/etc/systemd/system/nginx.service.d/override.conf
$ systemctl edit --full nginx                # 复制完整配置到 /etc/systemd/system 后编辑
$ systemctl revert nginx                     # 撤销所有本地覆盖

# 临时修改(重启后失效,但 service restart 仍有效)
$ systemctl set-property nginx MemoryMax=2G CPUQuota=150%
$ systemctl show nginx -p MemoryMax
```

drop-in 中清空一个已有配置项的写法是**先赋空值再赋值**：

```bash
[Service]
ExecStart=
ExecStart=/usr/local/bin/nginx -g "daemon off;"
```

## 3.3 Target 与运行级别

Target 是 systemd 对"系统状态"的抽象，用来替代 SysV 的运行级别（runlevel）。两者对应关系如下：

| SysV 运行级别 | systemd target | 说明 |
| ------------- | -------------- | ---- |
| 0 | `poweroff.target` | 关机 |
| 1 / s / single | `rescue.target` | 单用户救援模式 |
| 2 / 3 / 4 | `multi-user.target` | 多用户命令行模式（服务器默认） |
| 5 | `graphical.target` | 图形界面模式 |
| 6 | `reboot.target` | 重启 |
| - | `emergency.target` | 紧急模式，仅挂载根文件系统 |

```bash
$ systemctl get-default                      # 查看默认 target
$ systemctl set-default multi-user.target    # 设为命令行模式(服务器推荐)
$ systemctl isolate rescue.target            # 切到救援模式(当前会话状态)
$ systemctl list-dependencies multi-user.target      # 查看某 target 的依赖树
$ systemctl list-dependencies --reverse multi-user.target   # 反向依赖:谁依赖了它
$ systemctl --failed                         # 查看失败的 unit
$ runlevel                                   # 兼容旧命令,显示上一次与当前运行级别
```

> 💡 排查"开机卡住/服务启动顺序不对"时，`systemctl list-dependencies --reverse <unit>` 比逐个猜顺序有效得多。

## 3.4 journald 日志管理

journald 是 systemd 的日志子系统，把内核日志与应用日志统一收集到 `/var/log/journal/`（持久化）或 `/run/log/journal/`（仅内存，重启丢失）中。是否持久化取决于该目录是否存在。

```bash
$ mkdir -p /var/log/journal                    # 创建目录后 journald 才会持久化
$ chown -R root:systemd-journal /var/log/journal
$ chmod 2755 /var/log/journal
$ systemd-tmpfiles --create --prefix /var/log/journal
$ systemctl restart systemd-journald
```

### 3.4.1 journalctl 常用用法

```bash
$ journalctl -u nginx                        # 某服务的全部日志
$ journalctl -u nginx -f                     # 实时跟踪(替代 tail -f)
$ journalctl -u nginx -n 100 --no-pager      # 最近 100 行,不分页
$ journalctl -u nginx --since "10 min ago"   # 最近 10 分钟
$ journalctl -u nginx --since today --until "1 hour ago"
$ journalctl --since "2026-10-08 14:00:00" --until "2026-10-08 15:00:00"
$ journalctl -p err -b                       # 本次启动以来的所有错误级别日志
$ journalctl -b -1                           # 上一次启动的日志(排查重启前现场)
$ journalctl -k                              # 只看内核日志(等价 dmesg)
$ journalctl -o json-pretty -u nginx -n 1    # JSON 格式输出,便于程序处理
$ journalctl -o short-precise -u nginx       # 精确到微秒的时间戳
$ journalctl _PID=12345                      # 按字段过滤
$ journalctl -u nginx | grep -i "error"      # 组合 grep(注意会失去分页与颜色)
```

日志级别（`-p` 参数）：

| 级别 | 名称 | 说明 |
| ---- | ---- | ---- |
| 0 | `emerg` | 系统不可用 |
| 1 | `alert` | 必须立即处理 |
| 2 | `crit` | 严重错误 |
| 3 | `err` | 错误 |
| 4 | `warning` | 警告 |
| 5 | `notice` | 正常但重要 |
| 6 | `info` | 普通信息 |
| 7 | `debug` | 调试信息 |

### 3.4.2 日志容量控制与切割

journald 默认最多占用磁盘的 10%（且不超过 4G），超出后自动删除最旧的日志。生产环境建议按容量上限做显式限制。

```bash
$ journalctl --disk-usage                    # 查看当前日志占用
$ journalctl --vacuum-size=500M              # 清理到只剩 500M
$ journalctl --vacuum-time=7d                # 只保留最近 7 天
$ journalctl --vacuum-files=5                # 只保留 5 个日志文件

$ vim /etc/systemd/journald.conf
```

```bash
[Journal]
Storage=persistent                           # volatile(仅内存)/persistent(持久化)/auto
SystemMaxUse=2G                              # 日志目录最大占用
SystemKeepFree=1G                            # 至少保留的磁盘空闲空间
SystemMaxFileSize=200M                       # 单个日志文件上限
MaxRetentionSec=30day                        # 最长保留时间
MaxFileSec=1day                              # 单个文件的写入时长上限
ForwardToSyslog=yes                          # 同时转发给 rsyslog
RateLimitIntervalSec=30s                     # 限流窗口
RateLimitBurst=10000                         # 窗口内允许的最大日志条数
```

> ⚠️ `RateLimitBurst` 默认值较小。当应用瞬间打印大量日志时会看到 `Suppressed N messages` 提示，日志被内核丢弃。压测或排查高频日志问题时需要调大该值。
> 💡 若同时使用 rsyslog（`/var/log/messages`），journald 与 rsyslog 会各存一份。磁盘紧张时可通过 `ForwardToSyslog=no` 只保留一份。

### 3.4.3 日志排障实战思路

```bash
# 服务起不来,第一步:看状态与退出码
$ systemctl status myapp -l --no-pager
$ journalctl -u myapp -n 50 --no-pager --no-hostname

# 关键信息解读
# Active: failed (Result: exit-code) ... status=1/FAILURE      进程以非0退出
# Result: oom-kill                                             被内存限制杀掉
# Result: timeout                                             启动超时(需调整 TimeoutStartSec 或 Type)
# status=203/EXEC                                              ExecStart 路径不存在或无执行权限
# status=200/CHDIR                                             工作目录不存在
# Result: start-limit-hit                                      重启过于频繁被 systemd 暂停

# 绕过 systemd 直接手工运行 ExecStart 命令,确认是否程序自身问题
$ sudo -u appuser /usr/bin/java -jar /opt/app/app.jar
```

| 常见状态码 | 含义 | 处理 |
| ---------- | ---- | ---- |
| `203/EXEC` | 找不到可执行文件或无权限 | 检查 `ExecStart` 路径、SELinux 上下文 |
| `200/CHDIR` | 工作目录不存在 | 检查 `WorkingDirectory` |
| `1/FAILURE` | 进程返回非 0 | 手工执行命令复现，查看应用自身日志 |
| `oom-kill` | 被 OOM 杀掉 | 调大 `MemoryMax` 或排查内存泄漏 |
| `timeout` | 启动超时 | 换用正确的 `Type`（如 `forking`）或加大 `TimeoutStartSec` |
| `start-limit-hit` | 短时间内重启次数超限 | `systemctl reset-failed` 后修复根因 |

```bash
$ systemctl show myapp -p Restart -p RestartUSec -p StartLimitBurst -p StartLimitIntervalSec
$ systemctl reset-failed myapp               # 清除失败计数后重试
```

### 4.1.1 查看内核与系统信息

```bash
$ uname -a                                   # 内核版本、主机名、架构等全部信息
$ uname -r                                   # 只取内核版本号
$ uname -m                                   # 系统架构,如 x86_64、aarch64

$ cat /etc/os-release                        # 发行版信息(推荐用这个判断发行版)
$ cat /etc/redhat-release                    # RHEL/CentOS 系

$ cat /proc/cpuinfo | grep -c processor      # CPU 核心数
$ lscpu                                      # CPU 架构与拓扑
```

### 4.1.2 内核模块管理

内核模块（Kernel Module）是可以按需加载到内核的代码片段，让内核保持精简的同时支持各式硬件与功能。`lsmod` 显示的模块来自 `/proc/modules`，模块文件位于 `/lib/modules/$(uname -r)/`。

```bash
$ lsmod                                      # 列出已加载的模块及依赖计数
$ lsmod | grep -i nf                        # 过滤:如查看 netfilter 相关模块
$ modinfo nf_conntrack                       # 查看模块信息(路径/参数/依赖/作者)
$ modinfo -F filename ext4                   # 只取模块文件路径
$ modprobe -n -v nf_conntrack                # 只演示不实际加载(-n dry-run)
$ modprobe nf_conntrack                      # 加载模块(自动处理依赖)
$ modprobe -r nf_conntrack                   # 卸载模块及其无用依赖
$ insmod /path/to/xxx.ko                     # 直接插入模块(不处理依赖,少用)
$ rmmod xxx                                  # 直接移除模块(不处理依赖)
$ depmod -a                                  # 重新生成模块依赖关系(modules.dep)
$ modprobe -c | head                          # 查看生效的模块配置
```

开机自动加载与参数配置：

| 文件 / 目录 | 作用 |
| ----------- | ---- |
| `/etc/modules-load.d/*.conf` | 开机自动加载的模块列表，每行一个模块名 |
| `/etc/modprobe.d/*.conf` | 模块参数、别名与黑名单配置 |
| `/etc/modules` | Debian/Ubuntu 系的开机加载列表 |

```bash
$ cat /etc/modules-load.d/k8s.conf
br_netfilter
ip_vs

$ cat /etc/modprobe.d/blacklist.conf
blacklist floppy                             # 禁止自动加载
options nf_conntrack hashsize=65536          # 设置模块参数

$ sysctl net.netfilter.nf_conntrack_max      # 查看 conntrack 表上限
```

## 4.2 内核参数（sysctl）

内核的绝大多数运行时参数都暴露在 `/proc/sys` 下，目录结构与 sysctl 的点号命名一一对应（`/proc/sys/net/ipv4/ip_forward` 对应 `net.ipv4.ip_forward`）。

```bash
$ sysctl net.ipv4.ip_forward                 # 查看单个参数
$ sysctl -a | head -n 20                     # 查看全部参数
$ sysctl -a | grep -i swappiness
$ sysctl -w net.ipv4.ip_forward=1            # 临时修改(等效 echo 1 > /proc/sys/net/ipv4/ip_forward)
$ echo 1 > /proc/sys/net/ipv4/ip_forward     # 直接写 procfs

# 永久修改
$ vim /etc/sysctl.conf                       # 传统方式
$ vim /etc/sysctl.d/99-tuning.conf           # 推荐:用独立文件,便于管理
$ sysctl -p /etc/sysctl.d/99-tuning.conf     # 手动加载(注意:重启也会自动加载)
$ sysctl --system                            # 按顺序重新加载所有配置文件
```

生产环境调优常用参数：

| 参数 | 默认/建议 | 说明 |
| ---- | --------- | ---- |
| `net.ipv4.ip_forward` | 0 → 1 | 开启路由转发（做网关、NAT、Kubernetes 节点必需） |
| `net.core.somaxconn` | 128 → 4096 | 已完成三次握手的监听队列上限，高并发 Web 必调 |
| `net.ipv4.tcp_max_syn_backlog` | 1024 → 8192 | 半连接队列长度 |
| `net.ipv4.tcp_tw_reuse` | 0 → 1 | 允许复用 TIME_WAIT 连接（仅影响主动方，安全） |
| `net.ipv4.tcp_fin_timeout` | 60 → 30 | FIN_WAIT2 超时时间 |
| `net.ipv4.tcp_keepalive_time` | 7200 → 600 | TCP 保活探测间隔，及时摘除死连接 |
| `net.ipv4.ip_local_port_range` | 32768 60999 | 本地随机端口范围，短连接量大时需扩大 |
| `net.core.rmem_max` / `wmem_max` | 212992 → 16777216 | 单 socket 收发缓冲区上限 |
| `net.netfilter.nf_conntrack_max` | 65536 → 1048576 | conntrack 表上限，NAT/防火墙场景易打满 |
| `vm.swappiness` | 60 → 10 | 降低换出倾向，数据库服务器必调 |
| `vm.max_map_count` | 65530 → 262144 | 进程可拥有的内存映射区数量，Elasticsearch 必需 |
| `vm.overcommit_memory` | 0 → 1 | Redis 等场景建议设为 1，避免 fork 时分配失败 |
| `fs.file-max` | 依赖内存 | 系统级文件句柄上限 |
| `fs.inotify.max_user_watches` | 8192 → 524288 | 单用户 inotify 监视数量，文件多的项目构建时必需 |
| `kernel.pid_max` | 32768 → 4194304 | PID 上限，容器密集环境容易耗尽 |
| `kernel.sem` | - | 信号量参数，Oracle 等数据库需按官方文档调整 |
| `kernel.msgmax` / `msgmnb` | - | 消息队列单条/单队列上限 |

> ⚠️ 改内核参数前先用 `sysctl <参数>` 记录原值，并逐台灰度而非全量下发。`tcp_tw_recycle` 在 NAT 环境下会导致连接异常，已被内核移除，不要再用。

## 4.3 系统启动流程

### 4.3.1 启动阶段总览

从按下电源到用户登录，Linux 的启动过程大致经过下面几个阶段：

| 阶段 | 组件 | 主要工作 |
| ---- | ---- | -------- |
| 1 | BIOS / UEFI | 硬件自检（POST），初始化设备，按启动顺序寻找引导设备 |
| 2 | Bootloader（GRUB2） | 读取引导配置，加载内核与 initramfs 到内存，传递内核参数 |
| 3 | 内核初始化 | 解压内核、初始化内存与设备驱动、挂载 initramfs 作为临时根文件系统 |
| 4 | initramfs | 加载真正的根文件系统所需的驱动（如 RAID、LVM、加密），然后切换根目录 |
| 5 | 内核启动 1 号进程 | 挂载根文件系统（按 `/etc/fstab`），执行 `/sbin/init`（指向 systemd） |
| 6 | systemd | 按依赖关系并行启动各个 unit，最终进入默认 target |
| 7 | 登录服务 | 启动 getty / sshd 等，等待用户登录 |

其中 3 与 4 是交替进行的：内核在 initramfs 中运行，加载必要驱动后再把控制权交回内核，切换到真实根文件系统。

### 4.3.2 GRUB2 引导配置

```bash
$ cat /etc/default/grub                      # 用户级配置(不要直接改 grub.cfg)
$ cat /boot/grub2/grub.cfg | head -n 30      # 生成的引导菜单(RHEL 系路径)
$ ls /boot/grub2/                            # 也可以看 /boot/grub/ (Debian 系)

# 修改内核启动参数
$ vim /etc/default/grub
GRUB_TIMEOUT=5                               # 菜单等待秒数
GRUB_DEFAULT=0                               # 默认菜单项
GRUB_CMDLINE_LINUX="crashkernel=auto rhgb quiet"     # 追加内核参数
$ grub2-mkconfig -o /boot/grub2/grub.cfg     # RHEL/CentOS 重新生成
$ update-grub                                # Debian/Ubuntu 重新生成

# 单次生效(不修改配置文件,重启一次后失效)
$ grubby --update-kernel=/boot/vmlinuz-$(uname -r) --args="console=ttyS0,115200"
$ grubby --info=ALL                          # 查看所有内核条目及其参数
$ grubby --default-kernel                    # 查看默认启动的内核
```

常用内核启动参数：

| 参数 | 作用 |
| ---- | ---- |
| `rhgb quiet` | 图形化简化输出，服务器排查问题时建议去掉 quiet |
| `console=ttyS0,115200n8` | 串口重定向，便于带外管理与日志留存 |
| `crashkernel=auto` | 预留 kdump 内存，用于崩溃后抓取 vmcore |
| `nomodeset` | 禁用内核模式设置，图形卡驱动异常时的救急参数 |
| `selinux=0` / `enforcing=0` | 关闭 SELinux / 切换为宽容模式（临时排障用，不要长期使用） |
| `systemd.unit=rescue.target` | 直接进入救援模式 |
| `init=/bin/bash` | 直接进入 shell，用于重置密码等极端场景（需 remount 根分区为可写） |
| `ro` / `rw` | 根文件系统只读 / 读写挂载 |

### 4.3.3 initramfs 与 dracut

initramfs 是一个被压缩的 cpio 归档，内核启动早期将其解压成内存中的临时根文件系统。它的作用是在真实根文件系统还不可用时（如根在 LVM、软 RAID、加密卷上）提供必要的驱动与工具。RHEL/CentOS 用 `dracut` 生成，Debian 用 `update-initramfs`。

```bash
$ ls /boot/initramfs-$(uname -r).img        # initramfs 文件
$ lsinitrd /boot/initramfs-$(uname -r).img | head -n 20     # 查看其内容
$ lsinitrd /boot/initramfs-$(uname -r).img | grep -i "lvm\|raid"

# 重新生成(内核参数或存储驱动变化后需要)
$ dracut -f -v /boot/initramfs-$(uname -r).img $(uname -r)
$ dracut -f                                  # 简写,重建当前内核的 initramfs
$ update-initramfs -u -k all                 # Debian/Ubuntu
```

### 4.3.4 systemd 启动分析与性能

```bash
$ systemd-analyze                            # 总启动耗时(内核 + 用户空间)
$ systemd-analyze time                       # 同上,更明确
$ systemd-analyze blame                      # 按耗时排序的启动项(找到拖慢开机的服务)
$ systemd-analyze critical-chain             # 关键启动链,定位真正的瓶颈
$ systemd-analyze critical-chain sshd.service
$ systemd-analyze plot > /tmp/boot.svg       # 生成可视化时序图
$ systemd-analyze verify /etc/systemd/system/myapp.service   # 校验 unit 语法

```

> 💡 `blame` 里耗时最长的项不一定是瓶颈，要看 `critical-chain` 的结果——不在关键链上的任务再慢也不会拖慢整体启动。

### 4.3.5 启动故障处理

系统启动失败是运维最紧张的场景之一，按"先进入系统、再修复配置"的思路处理。

```bash
# 场景一:忘记 root 密码(GRUB 菜单可交互)
# 1. 在 GRUB 菜单按 e 编辑启动项
# 2. 在 linux 行末尾追加  rd.break  或  init=/bin/bash
# 3. 按 Ctrl+X 启动,进入 shell 后:
mount -o remount,rw /sysroot                # rd.break 方式:先挂载为可写
chroot /sysroot
passwd root
touch /.autorelabel                          # SELinux 开启时必须执行,否则无法登录
exit
reboot -f

# 场景二:fstab 写错导致启动卡在紧急模式
# 进入 emergency shell 后
mount -o remount,rw /                        # 把根分区重新挂载为读写
vi /etc/fstab                                # 修正错误条目(注意 UUID 与挂载点)
mount -a                                     # 验证 fstab 配置是否正确(关键一步)
systemctl daemon-reload
reboot

# 场景三:进入救援模式排查
# 同样在 GRUB 编辑界面把整行改为:
# linux16 /vmlinuz-xxx root=/dev/mapper/xxx ro systemd.unit=rescue.target
```

| 故障现象 | 常见原因 | 处理 |
| -------- | -------- | ---- |
| 卡在 `emergency mode` | fstab 有错、根分区损坏、UUID 变化 | 按场景二处理，`mount -a` 验证 |
| 卡在 `rescue` 并提示输入密码 | 磁盘检查失败或关键服务起不来 | 查看 `journalctl -xb` 定位失败 unit |
| 启动后黑屏 / 驱动异常 | 显卡驱动或内核参数问题 | GRUB 追加 `nomodeset` |
| 内核 panic | 内核与硬件不兼容、initramfs 缺失驱动 | 选择旧内核启动，检查 `/boot` 与 `dracut` |
| 内核升级后无法启动 | 新内核缺少存储驱动 | 菜单选择旧内核，重做 initramfs |

```bash
$ journalctl -xb                             # 本次启动全部日志(救援模式下最好用)
$ journalctl -xb -p err                      # 只看错误
```

# 5 终端复用方法

## 5.1 终端复用概述

### 5.1.1 为什么需要终端复用

通过 SSH 登录服务器执行任务时会遇到两个绕不开的问题：一是网络抖动或终端关闭会让会话中的所有前台进程收到 SIGHUP 而中断；二是同一时间只能看到一个会话，切换任务要反复登录。终端复用器（Terminal Multiplexer）通过在服务器端维护一个常驻的"伪终端 + 会话"进程解决了这两个问题：客户端断开只会让会话"分离（detach）"，进程继续运行；重新连接后可以"再附着（attach）"回到原来的现场。

| 能力 | 说明 |
| ---- | ---- |
| 会话保持 | 客户端断开后进程不受影响，长任务安全 |
| 多窗口 / 分屏 | 一个 SSH 连接内并行处理多个任务 |
| 会话共享 | 多个客户端附着同一会话，适合远程协作排障 |
| 输出留存 | 可开启日志记录，保留完整执行过程 |

### 5.1.2 常用方案对比

| 方案 | 断线后进程存活 | 可重新接管 | 分屏 | 会话共享 | 适用场景 |
| ---- | -------------- | ---------- | ---- | -------- | -------- |
| `nohup cmd &` | 是 | 否（只能看日志） | 否 | 否 | 简单的后台任务 |
| `setsid cmd` | 是 | 否 | 否 | 否 | 彻底脱离终端的守护进程 |
| `screen` | 是 | 是 | 支持（较弱） | 支持 | 老系统兼容性最好，几乎预装 |
| `tmux` | 是 | 是 | 支持（更强） | 支持 | 当前首选，配置灵活、脚本友好 |
| `byobu` | 是 | 是 | 支持 | 支持 | 在 screen/tmux 之上的易用封装 |

> 💡 两者本质相同：都是"服务端会话 + 客户端附着"的 C/S 结构，底层接口为 `/dev/ptmx` 伪终端。选择依据通常是——系统预装了什么就用什么，新环境优先 tmux。

## 5.2 screen 使用

`screen` 出现得更早，几乎所有发行版都已预装，兼容性最好，且不依赖配置文件即可直接用。它的默认前缀键是 `Ctrl+A`。

### 5.2.1 会话管理

```bash
$ screen                                     # 新建一个会话
$ screen -S deploy                           # 新建会话并命名(强烈建议命名)
$ screen -ls                                 # 列出所有会话及其状态
There is a screen on:
        20481.deploy    (Detached)
1 Socket in /var/run/screen/S-root.

$ screen -r deploy                           # 重新附着到指定会话
$ screen -r 20481                            # 也可以用 PID
$ screen -d deploy                           # 强制分离(在别处仍打开时使用)
$ screen -d -r deploy                        # 先分离别处的会话,再附着到本地(最常用)
$ screen -x deploy                           # 多人共享附着(不分离其他客户端)
$ screen -dmS watch_job top                  # 后台新建会话并直接执行命令(脚本常用)
$ screen -wipe                               # 清理已死掉的会话
$ exit / Ctrl+A d                            # 退出会话 / 暂时分离
```

```bash
# 典型场景:跑一个长任务,断开 SSH 后任务继续
$ screen -S backup
$ /usr/local/bin/backup_full.sh              # 执行长任务
# 按 Ctrl+A 再按 d 分离,然后可以安心关掉终端
# 下次登录后
$ screen -d -r backup                        # 直接回到任务现场
```

### 5.2.2 screen 常用快捷键

所有按键都以 `Ctrl+A` 作为前缀（下面简写为 `C-a`），先按前缀再按功能键。

| 按键 | 作用 |

| `C-a d` | 分离当前会话（detach） |

| `C-a 0-9` | 切换到编号为 0-9 的窗口 |
| `C-a "` | 列出所有窗口并选择 |
| `C-a A` | 重命名当前窗口 |
| `C-a N` | 查看当前窗口名称与编号 |
| `C-a k` | 关闭当前窗口 |
| `C-a '` | 切换到指定编号或名称的窗口 |
| `C-a S` | 水平分屏 |
| `C-a ` | 垂直分屏 |
| `C-a Tab` | 在分屏区域之间切换 |
| `C-a X` | 关闭当前分屏区域 |
| `C-a Q` | 关闭除当前外的所有分屏 |
| `C-a [` | 进入复制模式（可用方向键/PageUp 翻页） |
| `C-a ]` | 粘贴复制缓冲区内容 |
| `C-a H` | 开始/停止把当前窗口输出写入日志文件 |

### 5.2.3 screen 配置文件 ~/.screenrc

默认的 screen 没有状态栏、滚动回看行数也很少，建议做一次基础配置。

```bash
$ vim ~/.screenrc
```

```bash
# 关闭启动问候信息
startup_message off
# 回滚缓冲区行数(默认只有 100,排查问题时非常不够用)
defscrollback 20000
# 关闭闪烁提示
vbell off
# 总是显示状态栏(窗口号、标题、负载、时间)
hardstatus alwayslastline
hardstatus string '%{= kG}[ %{G}%H %{g}][%= %{= kw}%?%-Lw%?%{r}(%{W}%n*%f%t%?(%u)%?%{r})%{w}%?%+Lw%?%?%= %{g}][%{B} %Y-%m-%d %{W}%c %{g}]'
# 用 Ctrl+A A 快速切换到上一个窗口
bind A other
# 支持 256 色
termcapinfo xterm* ti@:te@
# 默认 shell
shell -$SHELL
```

> 💡 `defscrollback` 是最值得改的一项：默认 100 行意味着故障时只能看到寥寥几屏输出，改到 20000 后 `C-a [` 才能翻出完整的报错现场。

## 5.3 tmux 使用

`tmux` 是目前的主流选择，相比 screen 的优势在于：分屏能力更强且可自由调整、配置语法更清晰、支持命令式操作与脚本化（`tmux send-keys`、`tmux capture-pane`），并有活跃的生态。它的默认前缀键是 `Ctrl+B`。

tmux 有三个层次的概念：**会话（session）** 对应一次完整的工作环境，**窗口（window）** 相当于一个全屏标签页，**窗格（pane）** 是窗口内的分屏。

### 5.3.1 会话与窗口管理

```bash
$ tmux                                      # 新建会话
$ tmux new -s deploy                        # 新建并命名会话
$ tmux new -d -s deploy                     # 后台新建会话(不附着)
$ tmux new -d -s deploy '/usr/local/bin/deploy.sh'    # 后台新建并执行命令
$ tmux ls / tmux list-sessions              # 列出所有会话
$ tmux attach -t deploy                     # 附着到指定会话
$ tmux a                                    # 附着到最近使用的会话
$ tmux a -t deploy -d                        # 先分离其他客户端再附着
$ tmux rename-session -t 0 prod             # 重命名会话
$ tmux kill-session -t deploy               # 关闭会话
$ tmux kill-server                          # 关闭所有会话(慎用,会终止全部任务)
$ tmux switch-client -t prod                # 在会话之间切换
$ tmux has-session -t deploy || tmux new -d -s deploy    # 脚本中判断会话是否存在
```

窗口与窗格的关键操作（前缀键统一为 `Ctrl+B`，下表简写为 `C-b`）：

| 按键 | 作用 |
| ---- | ---- |
| `C-b d` | 分离会话（detach） |
| `C-b s` | 列出并切换会话 |
| `C-b $` | 重命名当前会话 |
| `C-b c` | 新建窗口 |
| `C-b n` / `C-b p` | 下一个 / 上一个窗口 |
| `C-b 0-9` | 切换到指定编号窗口 |
| `C-b ,` | 重命名当前窗口 |
| `C-b w` | 列出所有窗口 |
| `C-b &` | 关闭当前窗口（会二次确认） |
| `C-b f` | 按窗口名查找 |
| `C-b ` | 左右分屏（垂直切分） |
| `C-b "` | 上下分屏（水平切分） |
| `C-b 方向键` | 在窗格之间切换 |
| `C-b o` | 顺时针切换到下一个窗格 |
| `C-b z` | 放大 / 还原当前窗格（临时全屏，非常实用） |
| `C-b x` | 关闭当前窗格 |
| `C-b {` / `C-b }` | 与相邻窗格交换位置 |
| `C-b !` | 把当前窗格拆分为独立窗口 |
| `C-b 空格` | 循环切换内置布局 |
| `C-b Alt+方向键` | 调整窗格大小 |
| `C-b t` | 在当前窗口显示时钟 |
| `C-b ?` | 列出所有快捷键绑定 |
| `C-b :` | 进入命令模式（所有操作都可用命令实现） |

> 💡 `C-b z`（放大窗格）是日常使用频率最高的一个：临时把一个小窗格铺满整个窗口，看完再按一次还原，比反复切换窗口高效得多。

### 5.3.2 tmux 配置文件 ~/.tmux.conf

```bash
$ vim ~/.tmux.conf
```

```bash
# 把前缀键改为 Ctrl+A(与 screen 习惯一致,且 Ctrl+B 在 vim 中另有用途)
set -g prefix C-a
unbind C-b
bind C-a send-prefix

# 以 1 开始编号,更符合直觉
set -g base-index 1
setw -g pane-base-index 1
set -g renumber-windows on

# 滚动缓冲区行数
set -g history-limit 50000

# 开启鼠标:点击切换窗格、拖动调整大小、滚轮翻页
set -g mouse on

# 关闭自动重命名(便于用窗口名表达任务含义)
setw -g automatic-rename off
set -g allow-rename off

# 分屏时继承当前目录
bind % split-window -v -c "#{pane_current_path}"
bind '"' split-window -h -c "#{pane_current_path}"

# 用 vim 风格在窗格间跳转
bind h select-pane -L
bind j select-pane -D
bind k select-pane -U
bind l select-pane -R

# 重载配置
bind r source-file ~/.tmux.conf \; display "配置已重新加载"

# 状态栏
set -g status-interval 5
set -g status-left "[#S] "
set -g status-right "#{?#{==:#{host},localhost},,#{host} }%Y-%m-%d %H:%M"
setw -g window-status-current-style bg=green,fg=black,bold

# 快捷键冲突规避:tmux 内需要 C-a 时连按两次
set -sg escape-time 10

# 终端与颜色
set -g default-terminal "screen-256color"
set -ga terminal-overrides ",*256col*:Tc"
```

### 5.3.3 tmux 复制模式与输出导出

在默认键位下，进入复制模式用 `C-b [`，退出用 `q` 或 `Esc`。开启 `mouse on` 后可以直接用鼠标滚轮翻页。

| 按键（复制模式内） | 作用 |
| ------------------ | ---- |
| 方向键 / `hjkl` | 移动光标（vim 风格还支持 `w`、`b`、`gg`、`G`） |
| `Ctrl+U` / `Ctrl+D` | 向上 / 向下翻半页 |
| `Ctrl+B` / `Ctrl+F` | 向上 / 向下翻整页 |
| `空格` | 开始选择 |
| `回车` | 复制选中内容到 tmux 缓冲区 |
| `C-b ]` | 粘贴缓冲区内容 |
| `C-b C-b` | 在复制模式内发送前缀键（需 `send-prefix` 支持） |
| `q` | 退出复制模式 |
| `g` | 跳到缓冲区开头 |
| `C-b =` | 显示缓冲区列表 |

> ⚠️ tmux 3.0 之后复制模式默认使用 vi 风格键位；若是 emacs 风格，可用 `setw -g mode-keys vi` 显式指定。

把窗格输出导出到文件（排查时留存证据、脚本中抓取命令结果）：

```bash
# 方式一:把当前位置的完整可见文本导到文件(不中断会话)
$ tmux capture-pane -p -S - -t deploy:0.0 > /tmp/deploy_output.txt
$ tmux capture-pane -pJ -S -200 -t deploy > /tmp/last200.txt     # 只取最近 200 行并合并折行

# 方式二:开启持续记录管道(可从 tmux 内用 C-b : 执行,或外部命令)
$ tmux pipe-pane -t deploy -o 'cat >> /tmp/deploy_full.log'
$ tmux pipe-pane -t deploy                       # 不带命令表示关闭记录

# 方式三:在 tmux 内用 C-b : 执行
:pipe-pane -o 'cat >> /tmp/deploy_full.log'
```

`capture-pane` 与 `pipe-pane` 是 tmux 相比 screen 最实用的增强：前者用于"把已经发生的事抓出来"，后者用于"把之后发生的事记录下来"。

## 5.4 典型实战场景

### 5.4.1 长任务不因断网中断

备份、数据迁移、大文件压缩这类任务动辄几十分钟到几小时，必须放进复用会话中执行。

```bash
$ tmux new -s backup
$ tar -czf /data/backup_$(date +%F).tar.gz /data/app     # 执行长任务
# 按 C-b d 分离,然后可以放心关闭终端
# 稍后回到服务器
$ tmux a -t backup                          # 回到任务现场继续观察

# 更规范的做法:把输出保留到文件,避免滚动缓冲区被刷掉
$ tmux new -s backup 'bash -c "/usr/local/bin/backup_full.sh 2>&1 | tee /var/log/backup_$(date +%F).log"'
```

### 5.4.2 多人共用同一会话排障

需要多人同时观察同一个操作过程时（远程协助、教学、交接），复用器可以直接共享会话。

```bash
# tmux:两人都以同一用户登录后
$ tmux a -t debug                            # 第二个客户端附着同一会话(自动共享)
$ tmux a -t debug -d                          # 从只读观察改为可操作,需踢掉对方

# 只读观察:附着后用 detach 的会话不可写,或直接看输出
$ tmux capture-pane -p -t debug              # 抓取当前画面,不干扰对方

# screen:共享会话需显式使用 -x
$ screen -x deploy
```

> ⚠️ tmux/screen 共享的是同一个 shell 进程，两人的光标与输入会互相干扰，不适合双方同时打字。更稳妥的方式是让一方操作、另一方用 `capture-pane` 或共享屏幕工具观察。

### 5.4.3 一屏掌握多个服务状态

```bash
$ tmux new -s ops
# 在 tmux 内执行:
# C-b %          左右分屏
# C-b "          上下分屏
# 在各窗格分别执行:
$ tail -f /home/swgx/8082/logs/error.log
$ tail -f /home/swgx/8082/logs/app.log
$ top
# C-b z 放大当前窗格,C-b 方向键 切换,C-b Alt+方向键 调整大小
```

```bash
# 直接在命令中一次创建好布局(可写入 ~/.bashrc 或脚本)
$ tmux new-session -d -s ops -n logs
$ tmux split-window -h -t ops
$ tmux split-window -v -t ops
$ tmux send-keys -t ops:0.0 'tail -f /home/swgx/8082/logs/error.log' C-m
$ tmux send-keys -t ops:0.1 'tail -f /home/swgx/8082/logs/app.log' C-m
$ tmux send-keys -t ops:0.2 'top' C-m
$ tmux attach -t ops
```

### 5.4.4 脚本中的 tmux 自动化

```bash
# 会话不存在才创建(幂等写法)
$ tmux has-session -t deploy 2>/dev/null || tmux new-session -d -s deploy

# 向已有会话发送命令并保留现场
$ tmux send-keys -t deploy '/usr/local/bin/restart.sh' C-m
$ sleep 5
$ tmux capture-pane -p -t deploy -S -50      # 抓取执行结果做校验

# 等待命令执行完成后再退出(用于 CI/CD 或批处理)
$ tmux send-keys -t deploy 'deploy.sh; echo DONE_MARKER' C-m
$ while ! tmux capture-pane -p -t deploy | grep -q DONE_MARKER; do sleep 5; done
```

`send-keys` 中的 `C-m` 表示回车（不能用引号包住），`C-c` 表示发送 `Ctrl+C`，这两个是最常用的控制键写法。

## 5.5 与 systemd 的取舍和常见问题

### 5.5.1 会话复用还是 systemd

会话复用解决的是"人不在终端前时任务能不能继续"，而 systemd 解决的是"服务能否长期可靠运行"。两者的分工建议如下：

| 需求 | 推荐方案 | 说明 |
| ---- | -------- | ---- |
| 临时跑一个耗时脚本 | tmux / screen | 有交互、需要随时回看输出 |
| 需要定期执行的任务 | cron / systemd timer | 见 3 计划任务和Systemd |
| 需要开机自启的长期服务 | systemd service | 支持自动重启、资源限制、日志统一 |
| 临时的后台任务（不想写 unit） | `systemd-run` | 由 systemd 托管，日志可查、资源可限 |
| 用户级常驻任务 | `systemctl --user` + `loginctl enable-linger` | 用户退出后仍运行 |

```bash
# 用 systemd 托管一次性任务(无需编写 unit 文件)
$ systemd-run --unit=big-backup /usr/local/bin/backup_full.sh
$ systemctl status big-backup
$ journalctl -u big-backup -f

# 带资源限制的临时任务
$ systemd-run --scope -p MemoryMax=1G -p CPUQuota=50% /usr/local/bin/report.sh

# 用户级服务:让用户退出登录后任务仍继续
$ loginctl enable-linger zmf
$ loginctl show-user zmf | grep Linger
```

> 💡 判断标准很简单：**"任务结束后进程就该消失"用复用会话或 `systemd-run`；"进程应该一直在那儿"用 systemd service**。用 tmux 长期托管生产服务是不可靠的——服务器重启后会话不会自动恢复。

### 5.5.2 常见问题排查

| 现象 | 原因 | 处理 |
| ---- | ---- | ---- |
| `tmux a` 提示 `no sessions` | 会话已被关闭，或用了不同用户登录 | `tmux ls` 确认；会话是按用户隔离的，必须用同一系统用户附着 |
| `screen -r` 提示 `Attached` 但无法附着 | 会话已在别处打开 | 用 `screen -d -r` 或 `tmux a -t xxx -d` |
| 字体/颜色显示异常 | 终端类型或颜色数设置不当 | 设置 `export TERM=xterm-256color`；tmux 中配置 `default-terminal` |
| 中文显示为乱码 | 服务器或客户端 locale 不一致 | 检查 `locale`，配置 `LANG=zh_CN.UTF-8` 或统一使用 `en_US.UTF-8` |
| 会话内方向键变成乱码 | `TERM` 与实际终端不匹配 | 会话内执行 `export TERM=screen-256color`（tmux）或 `screen` |
| 嵌套进入多层会话后快捷键失效 | 前缀键被外层会话捕获 | 连按两次前缀键把按键透传给内层；或换用不同前缀键 |
| `Ctrl+B` 与 vim/tmux 冲突 | vim 中 `Ctrl+B` 是翻页 | 把 tmux 前缀改为 `Ctrl+A` |
| 会话进程被 OOM 杀掉 | 长任务内存超限 | 参考 1 进程和内存管理，用 `MemoryMax` 限制并关注 `oom_score` |
| 关掉终端后任务仍在但输出找不到 | 输出未落盘，随终端销毁 | 启动时用 `tee` 或 `pipe-pane` 保留日志 |
| `tmux` 启动报 `server exited unexpectedly` | 旧会话文件损坏或 `/tmp` 权限异常 | 删除 `/tmp/tmux-*` 后重试，检查 `/tmp` 权限 |

### 5.5.3 使用建议小结

- 养成"长任务先进 tmux/screen"的习惯，可以避免绝大部分"跑到一半断线"的事故
- 会话一定要命名（`-s`），并定期用 `tmux ls` / `screen -ls` 清理残留会话，防止长期不用的会话占住内存与进程
- 重要任务的输出务必落盘（`tee`、`pipe-pane`、`screen -L`），终端滚动缓冲区不是可靠的记录载体
- 把常用的会话与分屏布局写成脚本或函数，可显著减少重复劳动
- 复用会话是**运维辅助手段**，不应作为生产服务的托管方案，长期运行的服务一律交给 systemd
